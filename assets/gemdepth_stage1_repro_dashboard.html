为什么帧数会系统性影响分数：eval.py 对整条序列拟合一组全局 scale+shift（视差空间 lstsq）再算 AbsRel。 序列越短，一组仿射参数越容易拟合得好；序列越长，模型的尺度漂移逐帧累积，一组全局仿射兜不住。 所以帧数越少，视频深度方法的分数系统性越好看——这不是噪声，是有方向的偏差。

Sintel 那 +0.2% 是个有用的对照：本次 DATASETS 里 Sintel 没切 500 协议，结果几乎不变（差异纯属 bf16 推理噪声）， 反证了流程本身没有引入偏差，其余三集的劣化是真实的协议效应。

五、Stage-2-lite 已训完 已评测 · null result

⚠ 先讲清楚定性：论文的 Stage-2 无法严格复现，本实验只是「机制近似」。 论文 3.5 节：Stage-2 = 冻结 GEM + 微调其余，数据 = IRS 100K + 野外立体视频 150K（均无位姿 GT），总 940K 帧。
  • 那 150K 野外立体视频作者从未公开，官方 README 的 Training Data 只列了 7 个可下载的集，其中并无此项。
  • IRS 唯一下载入口是 OneDrive（GitHub 仓库只有代码），HuggingFace 无镜像。
因此结论中绝不能写「复现了 Stage-2」，只能写「Stage-2 机制的近似消融」。

Stage-2 到底在解决什么问题 已重写

❌ 作废的解释：旧看板写“Stage-1 用 GT 位姿喂网络，推理时没有 → ASTT 没训过带噪几何”——读代码后证伪。

GT 位姿从不进 forward，只进 loss（CameraLoss 里跟 pose_enc_list 比 L1）； 网络里流的一直是 GEM 自估的位姿： 
pose_enc_list = self.camera_head(concat_inter)   # GEM 自己算的
feats[3] += pose_quats_features + pose_trans_features + pose_trans_scale_features
训练与推理数据流一致，不存在硬性 mismatch。
✅ Stage-2 真实的三个机制：
机制说明我们测了吗
A 域适应合成 → 真实。占论文收益大头（Sintel −43.5%）❌ 没有真实数据
B 消除“移动靶”冻 GEM 后几何表示固定，ASTT 可充分收敛✅
C 释放容量去掉 Lcam，梯度全用于深度✅
⚠ 而且 pose_flag: false 在 gem_frozen 下其实是 no-op：Lcam 的梯度路径 camera_head → global/frame_blocks → camera_token/register_token → feats[3] → 冻结 backbone 全部落在 GEM_PREFIXES 里、已被冻住，没有可训练参数可更新。 所以 Stage-2-lite 的实质变量只有“冻 GEM + lr 降 10× + 多训 10k 步”。

★★ 代码里已经内置了位姿 dropout 新发现

model/gemdepth.py L319–334： 
overall_geometric_input_mask    = torch.rand(B)   < 0.9    # 10% 整段丢几何
per_sample_geometric_input_mask = torch.rand(B*T) < 0.95   #  5% 逐帧丢
per_sample_cam_input_mask       = torch.rand(B)   < 0.5    # 50% 整段丢相机
被 mask 的位置位姿被强制设为 identity（quat=[0,0,0,1], trans=0）， 实际约 43% 的帧拿到真实位姿、5 7% 拿到“没有位姿”。

这正对应论文 Table 9「50% 位姿注入 ≈ 100% 效果」（0.071 vs 0.070）。 → ASTT 对位姿缺失/噪声的鲁棒性是 Stage-1 就内置训好的，不需要 Stage-2 去补—— 这也从机制上解释了下面的 null result。
✅ P0 已确认并修复（2026-08-24）：推理一直是不确定的

逐行核实：model/gemdepth.py 全文没有任何 self.training，三个 torch.rand 在 GemDepth.forward 里无条件执行；而 evaluation/inference/infer.py、 eval_vkitti_dense.py 都确实调了 .eval()。两边合起来就是：
  • 每次评测约 57% 的帧随机被换成单位位姿（保留率 0.9×0.95×0.5 ≈ 43%）
  • 同一个 checkpoint 跑两次结果不同
  • 并且是系统性变差：推理时本来应该每帧都拿得到 GEM 自己预测的位姿
修法：抽出 GemDepth._pose_input_mask()，not self.training 时返回全 True； 训练分支保持位不变。单测 test/test_pose_input_mask.py 锁住（含“推理不消耗全局 RNG”）。

影响面（已逐个 config 核实，比最初估的窄很多）： 该代码整段在 if self.use_gem: 里，所以只打到开了 GEM 的跑：
  • ✅ 受影响：config/stages/stage1_repro、stage2_lite（显式 true）， 以及 stages/stage1、stage2、single_a100/*（未设 → factory.py 默认 True）。即本页的四集数字与 Stage-2-lite。
  • ❌ 不受影响：config/scratch/** 全部（含两个 mixdata 8gpu）、 config/vkitti/*、multilevel_decoder —— 它们 use_gem: false。 ConvNeXt pyramid 骨干强制如此（gemdepth.py 里有断言），结构性免疫。
受影响的那批数字既带额外方差，也少用了一半几何信息。 之前归因为 bf16 的 0.0778 vs 0.0780、Stage-2-lite 的 ±0.9%，现在都有了更直接的解释。 需重新评测已有 checkpoint 才能得到可引用的数字（无需重训）。

ckpt 层面的决定性验证（不看 config 看权重，use_gem 未设时默认 True 容易漏判）： 数一下 state_dict 里 camera_head/camera_token/global_blocks/cam_*_encoder 前缀的键 —— single_a100_{baseline,errormap,em_single} 各 163 个， vkitti_baseline 0 个。两边完全对上。
⚠ 别漏了 single_a100/* 这条老线 —— 它也开着 GEM。 不过复核后并不阻塞当前工作，两种情况：
  • single_a100_multiscale_fix = 历史最佳多尺度 0.0725 —— ckpt 已不存在（软链目标下只剩 baseline / errormap / em_single）， 全盘搜索也没有。该数字永久无法复核，此后不得再引用。
  • single_a100_errormap / em_single = errmap 老实验，ckpt 还在。 但它们的数字并未被任何在用结论引用 —— errmap 的对照组是 我们自己的 stage1_repro（见 HANDOVER_gemdepth_stage1.md）， 不是这批老跑。所以重测它们是可选项，不是前置条件。
真正必须重测的只有 stage1_repro（在用数字 + errmap 对照组）与 stage2_lite（null result 结论所依赖）。
订正一条自己的说法：“±0.0006 种子噪声带一并作废”—— 说过头了。

那个带是从 E2a_feedback_s1/s2 量出来的，属于 ConvNeXt use_gem: false 一族， 不受本 bug 影响，在 scratch/mixdata 系列里仍然成立。 真正的问题是：它从来就不该被拿去判 GEM 模型（stage1_repro / stage2-lite）的差异， 而后者目前没有任何已测的噪声带—— 这才是空白所在。
顺带发现（未改，会变训练语义）：.repeat(T) 对齐错位

rand(B).repeat(T) 把 (B,) 抽样平铺成 [b₀..b_{B-1}] × T， 但被掩的那个轴是 (B,T) 展平的（下标 b*T+t，看 pose_trans_across_views.unflatten(0,(B,T)) 可确认）。 VKITTI 配置下 B=16/卡、T=4，B≠T → “整段 clip 一起丢位姿”的语义退化成了逐帧噪声。 边际概率（0.9 / 0.95 / 0.5）不变，所以一直没被发现。 改成 repeat_interleave(T) 会改变训练行为并作废与现有跑的可比性， 因此只在代码里加了 NOTE，未擅自修改。

另一处未复现的配置：多分辨率训练 新发现

论文 A.2：短边 resize 到 518 + 随机中心裁剪，产生 6 种分辨率 518×518 / 518×392 / 518×336 / 518×294 / 518×252 / 518×168（时序长度都是 32）， 目的是让网络泛化到不同宽高比。我们只用了单一 518×518。 另：论文对所有室外数据集将天空深度截断到 400 做监督（我们 mvs_synth 用 500）； PointOdyssey 只用有背景深度 GT 的子集（follow FlashDepth）。
