VKITTI 多尺度头 vs Temporal 基线 —— 对照实验看板

PP-DPT · 分支 feat/registry-mixdata (PR#8 注册表重构后) · 训练 2026-08-21 → 08-24 · 阿里云 DSW 8×H20 · 评测日期 2026-08-24

0. 一句话结论

域内赢、泛化输 —— 符号翻转。 多尺度 refine 头在训练域 VKITTI 上比同配方 temporal 基线好 5.8%（AbsRel 0.1192 → 0.1123）， 但换到 KITTI zero-shot 就反过来落后 2.3%（0.0981 → 0.1004），RMSE / δ1 同向落后。 这更像容量与等效学习率带来的过拟合，而不是头结构的方法增益。 在补齐两个消融 arm 之前，不得宣称多尺度头优于 temporal。
✅ 已排除：同日修的那个位姿 dropout P0，对本页三路无影响。 model/gemdepth.py 的位姿 dropout 缺 self.training 守卫，推理时会随机抹掉约 57% 帧的位姿。 但那整段代码在 if self.use_gem: 里，而三个 arm 都是 use_gem: false / use_astt: false（ConvNeXt pyramid 骨干强制要求如此， 见 gemdepth.py 的 backbone_format == 'pyramid' 断言）—— 根本不执行。 该 P0 只涉及 config/stages/ 下的 GemDepth 正统复现线。 本页数字无需重测。

3. 代码层面：ms 相对基线多了什么

基线出深度（model/dpt_convnext.py）

path_1 = refinenet1(...)                 # 224²
out = scratch.output_conv1(path_1)       # 256 → 128
out = interpolate(out, 448²)             # 特征先上采样
with autocast(enabled=False):            # ← 无条件 FP32
    out = scratch.output_conv2(out.float())   # 128 → 32 → 1

多尺度头（model/dpt_multiscale_convnext.py）

for i, feat in enumerate([path_4(28²), path_3(56²), path_2(112²), path_1(224²)]):
    out_size = min(feat*2, 448)                        # 56 / 112 / 224 / 448
    f = output_conv1_heads[i](feat)                    # 256 → 128
    f = interpolate(f, out_size)
    e = depth_encoder(resize(depth_prev.detach()))     # 1 → 32   深度反馈
    delta = delta_heads[i](cat[f, e])                  # 160 → 32 → 1
    depth_i = resize(depth_prev).detach() + delta      # 残差累积
训练返回 4 个尺度；eval 返回 scale_depths[-1]（448²，与基线同分辨率）
结构上，ms ≈ 把基线的 output_conv1/output_conv2 在四个尺度各复制一份，再给每份额外喂一张上级深度图。

4. 关于 multiscale_fp32_head（一条订正）

订正：在本次对照里 fp32_head: true 才是同口径的那个 arm。 基线的 scratch.output_conv2 在代码里是 无条件 FP32（with autocast(enabled=False) 写死）。 师兄 config 开 true 是刻意与基线对齐，不是随手打开的。 我们额外加的 nofp32 arm 反而多引入了一个变量。
历史上"fp32_head 是负结果"的结论不适用于此处。 那来自 mixdata 配方下 E2a/E4 两组消融（各退化约 0.003 ≈ 种子噪声 5 倍），是另一套代码与数据配比。 本次两个协议还打架：VKITTI 域内 fp32 更好（0.1123 vs 0.1155），KITTI 上 nofp32 更好（0.0991 vs 0.1004）， 差距 0.0013–0.0032，在本次样本量下判不出优劣。

5. 必须标注的局限（诚实清单）

  • VKITTI 域内样本量极小：1 条 held-out 序列 / 268 帧。历史实测的种子噪声带是 AbsRel ±0.0006（在四集 benchmark 上），单序列方差只会更大。
  • VKITTI val 帧训练时见过：train split 的 end_idx = round(seq_num) = 0–100%，val 取后 10% 落在训练集内。域内数字系统性偏乐观，只能当 sanity / 对照，绝对值不可对外引用。
  • 单 seed：三个 arm 都只有 seed 0。KITTI 上 2.3% / 1.0% 的差距未经多种子确认。
  • loss 尺度不匹配：见 §1 的对照缺陷，尚未消除。
  • 头结构已与历史 E 系列不同：PR#8 之后是"特征先上采样再出残差 + depth_feedback 恒开"，fullres_mode 退化成死开关。 不能把本次数字与历史 C / E1 / E2a / E3 / E4（0.0915–0.0946 那批）横向比较。
  • KITTI 用 110 帧短协议（kitti_video.json），不是论文的 500 帧协议。短协议对视频方法系统性偏乐观（实测 kitti 短→500 会劣化约 10.8%）。

8. 本轮踩坑记录

  • 首轮两个 ms arm 全部 Exit 1：TypeError: MultiScaleVideoDepthLoss.__init__() got an unexpected keyword argument 'normalize_scale_weights'。 根因是阿里云工作树版本错配——train.py 是新版会传该参数，loss/multiscale_videoloss.py 还是旧版。 起因是之前用 git checkout FETCH_HEAD -- <部分文件> 挑文件时漏了 loss/。 修法：git checkout FETCH_HEAD -- loss/multiscale_videoloss.py。
  • torchrun 只在末尾留 <NO_OTHER_FAILURES> 尾巴，真因在其上方的 Root Cause 段 —— tail -2 看不到，要 tail -60。
  • 日志里 tqdm 的 \r 会把后续 print 挂在同一"行"上，grep "^\[loss\]" 只匹配到第一条； 要先 tr '\r' '\n'。含控制字符的日志还需 grep -a，否则报 "binary file matches"。
  • 多尺度未退化：step 0 四尺度 total_loss = 3.3313 / 3.2473 / 2.8966 / 3.3724（不全等）， 历史上"多尺度塌缩成单尺度"的老毛病没有复发。
